This option replaces the Fargate relay and MSK Serverless broker used by Options A and B. The **relay runs on
a single EC2 instance** in a public subnet, writes each telemetry record to **Amazon DynamoDB**, and the
`telemetry-server` Lambda queries the table when a client calls `GET /telemetry/latest`. The read API stays
the same HTTP API as Option A.

## How a request flows

1. **Device → EC2 relay.** Devices open a WebSocket to port 9000 on the relay's public IP. The relay
   container is started by `user_data` from the `telemetry-relay` image in ECR.
2. **Relay → DynamoDB.** Each record is written to the on-demand `telemetry` table as an item with partition
   key `pk` and numeric sort key `sk` (the record timestamp). This replaces the Kafka publish step.
3. **Client → API Gateway → Lambda.** The HTTP API forwards `GET /telemetry/latest` to the Lambda in the
   private subnet.
4. **Lambda → DynamoDB.** The function queries the table for the newest records and returns them as JSON,
   replacing the in-memory ring buffer fed by the Kafka consumer.

The EC2 instance has no key pair. Its logs go to the CloudWatch group
`/ec2/<project>-<env>-option-c/telemetry-relay`, and its instance profile grants ECR pull, DynamoDB
`PutItem` and CloudWatch Logs access. The Lambda role grants DynamoDB `Query`/`GetItem` instead.

## Application prerequisite

This option is Terraform-only. The images in ECR must be built with a DynamoDB publisher for the relay and a
DynamoDB reader for the server; the current images use the Kafka publisher and consumer. Instances of the
new option pass `DYNAMODB_TABLE` and `AWS_REGION` to both processes, and omit `KAFKA_BROKERS`/`KAFKA_TOPIC`.

## Expected load and cost estimate

The prod usage assumptions live in
`terraform/option-c-ec2-dynamodb/env/prod/c3x-usage.yml`. They match the other options: 1,000,000 HTTP API
requests and Lambda invocations per month, 200 ms average duration, 5 GB per ECR repository, 5 GB of relay
logs ingested and stored (0 GB scanned), and 50 GB of stored data. DynamoDB additionally assumes 1,000,000
writes and 1,000,000 reads per month.

`make tf-estimate TF_OPTION=option-c-ec2-dynamodb TF_ENV=prod` produces this monthly baseline for `us-east-1`
(730 hours). c3x uses the defaults in `variables.tf` — 512 MB Lambda memory and a `t3.micro` instance — not
the prod override of 1024 MB Lambda memory.

## Trade-offs

Option C costs **USD 537.52/month less** than Option A at the same load: MSK Serverless (USD 548.60) and
Fargate (USD 9.01) are replaced by EC2 (USD 7.59) and DynamoDB (USD 12.50). The HTTP API, Lambda, VPC, ECR
and log costs are unchanged.

The savings come with operational cost. The relay is a single EC2 instance in a public subnet with port 9000
open to `0.0.0.0/0` and a dynamic public IP that changes on stop/start — restrict the ingress CIDR or put an
ALB in front of it before production use. There is no automatic task replacement when the instance fails,
and the partition/sort key design must match the application's lookups. Choose this option when cost matters
more than managed availability and you can operate the EC2 host.

See the [overview](/docs/aws-deployment/overview) to compare all three options.
